# Sonic Transfer 设计规格

## 1. 目标

创建一个 Python 命令行工具，通过音频交叉线在 Windows 与 macOS 之间可靠传输单个约 200MB 的文件。两端使用全双工音频链路：文件数据沿发送方向传输，确认、流控、重传和控制信息沿反向通道传输。

首版聚焦于单文件、单发送方向；协议和模块接口保留双向数据帧能力，以便后续支持两端同时发送文件。

## 2. 范围与非目标

### 范围

- Windows 和 macOS 上运行的发送端与接收端。
- 48kHz、16-bit PCM 音频输入/输出。
- 通过独立的反向单声道通道实现双向通信。
- 单文件元数据、分块传输、校验、选择重传、断点恢复。
- 纯命令行操作和可观察的速率/错误日志。
- 虚拟音频信道测试，以及可选的真实设备回环测试。

### 非目标

- 不实现网络传输、加密或压缩；需要压缩时由用户预先处理文件。
- 不依赖大型音频框架、机器学习模型或系统级 modem 工具。
- 不保证在任意廉价声卡、极端噪声或自动增益环境下工作；工具应提供稳健模式和明确诊断。

## 3. 方案选择

候选方案包括 4/8-FSK、单载波 QPSK 和小型 OFDM。FSK 最容易实现但频谱效率不足；单载波 QPSK 速度较高但对频偏和音频链路失真更敏感；小型 OFDM 可通过多个子载波利用音频带宽，并使用导频跟踪频偏/相位，因此选择小型 OFDM + 差分 QPSK。

首版不引入复杂 FEC 库，采用 CRC32 检错与反向 ACK/NACK 选择重传。滑动窗口限制未确认帧数量，避免 200MB 文件传输时无限占用内存。

## 4. 系统架构

```text
CLI
 └── Session
      ├── FileSender / FileReceiver
      ├── Framing + CRC32 + metadata
      ├── Selective-repeat ARQ state
      ├── Modem: OFDM/QPSK encode/decode
      └── AudioDevice: RawInputStream / RawOutputStream
```

音频采集、调制播放、解调、协议状态机和文件 I/O 通过有界线程安全队列连接。音频回调只做固定时间块的入队/出队，不执行文件 I/O 或复杂协议逻辑，降低欠载/溢出风险。

### 模块职责

- `audio.py`：枚举设备，打开 RawInputStream/RawOutputStream，提供 PCM block 管道。
- `modem.py`：前导、同步、OFDM 符号、导频、差分 QPSK 的编码和解码；不负责文件协议。
- `protocol.py`：帧头、类型、序号、会话、CRC32 和元数据编解码。
- `arq.py`：发送窗口、ACK/NACK、超时、选择重传、重复帧处理和流控。
- `transfer.py`：文件读取/写入、`.part` 临时文件、SHA-256、断点状态。
- `cli.py`：`send`/`receive` 子命令、设备与调制参数、日志和退出码。

## 5. 音频与调制参数

- 采样率默认 48,000Hz，可通过 CLI 覆盖。
- 样本格式默认 signed 16-bit PCM；内部音频流优先使用 `sounddevice` RawStream，避免强制引入 NumPy。
- 每方向使用一个单独的单声道频带；默认保留约 4kHz–20kHz 的可用频带，并避开直流、极低频和明显工频干扰。
- OFDM 符号包含循环前缀、导频和约 24 个有效子载波。
- 数据调制使用差分 QPSK；稳健模式降低子载波数量/符号速率并增加保护间隔，速度模式使用默认参数。
- 实际吞吐不作硬编码承诺；工具必须报告有效 kbps、重传率和预计剩余时间。

## 6. 帧协议

每个逻辑帧先进行二进制封装，再交给调制器。帧包含：魔数/版本、会话 ID、帧类型、方向、序号、确认号、负载长度、负载和 CRC32。整数采用固定字节序，协议版本不兼容时应明确拒绝。

帧类型至少包括：`HELLO`、`FILE_INFO`、`DATA`、`ACK`、`NACK`、`FINISH`、`FINISH_ACK`、`ABORT` 和 `RESUME`。

`FILE_INFO` 传输 UTF-8 文件名、文件大小、分块大小和完整 SHA-256。`DATA` 负载大小受音频帧和窗口参数限制，发送端只保留窗口内未确认数据。接收端顺序写入或缓存少量乱序块，并以位图/范围形式确认连续序号。

## 7. 可靠性与恢复

- CRC32 失败的帧被丢弃，并在反向通道发送 NACK 或缺失范围。
- 超时由测得的往返时间和重传上限共同决定；连续失败超过阈值时终止会话并给出建议。
- 接收端写入 `filename.part` 和旁车状态文件，状态至少记录会话 ID、文件大小、分块大小、已确认范围和哈希进度信息。
- 重启后，接收端可根据文件名/大小/分块参数发出 `RESUME`；发送端验证元数据后从缺失块继续。
- 文件所有块收到且 SHA-256 匹配后，关闭并刷新临时文件，再原子改名为目标文件。
- 终止、设备断开、输入文件变化和协议版本错误都必须删除或保留状态文件，行为通过 CLI 日志明确显示。

## 8. CLI

发送：

```text
python -m sonic_transfer send PATH [--input-device ID] [--output-device ID]
                           [--mode robust|fast] [--resume] [--verbose]
```

接收：

```text
python -m sonic_transfer receive OUTPUT_DIR [--input-device ID] [--output-device ID]
                              [--mode robust|fast] [--resume] [--verbose]
```

另提供 `devices` 子命令列出音频设备。CLI 必须返回非零退出码表示失败，不打印文件内容，不覆盖已存在目标文件，除非用户明确提供覆盖选项（首版可暂不提供覆盖选项而使用唯一临时名）。

## 9. 依赖与平台

- Python 3.11 或更高版本。
- 运行时仅依赖 `sounddevice`；优先使用标准库完成协议、校验、文件处理和测试信道。
- `sounddevice` 依赖 PortAudio，安装文档必须说明 Windows/macOS 的声卡权限、输入输出设备选择和系统音量设置。
- 不假设发送端一定是 Windows、接收端一定是 macOS；两端程序行为由子命令决定。

## 10. 测试策略

1. 单元测试：帧封装/解析、CRC、元数据、QPSK/OFDM 基本往返、边界长度和版本拒绝。
2. 协议测试：使用内存信道测试乱序、重复、丢失、损坏、超时、窗口推进和断点恢复。
3. 文件测试：小文件、空文件、非对齐文件、中文文件名、哈希失败和中断恢复；不在测试中生成 200MB 常量文件，另设流式大文件测试。
4. 音频信道测试：对调制后的样本注入幅度变化、白噪声、频偏、丢帧和削波，验证稳健模式能报告失败而不是静默产出错误文件。
5. 集成测试：在同一台机器的两个虚拟/回环音频设备上运行 send/receive；真实交叉线测试作为手工验收流程。

## 11. 验收标准

- `pytest` 能通过协议、ARQ、文件恢复和虚拟信道测试。
- 命令行可列出设备，并能启动发送和接收会话。
- 接收文件的字节数和 SHA-256 与源文件一致。
- 注入可恢复的丢帧/损坏时，传输最终完成且报告重传；不可恢复时以非零退出码终止。
- 传输中断后重新运行 `--resume` 能从已有临时文件继续，而不是从零开始。
- 依赖和安装步骤在 README 中明确，项目不引入大型第三方库。
